## Connect from r5d

1. Sign in to Threadline and open **API access**. Create a personal key with **Read only** or **Read and write**, name it for the integration and choose an expiry.
2. Copy the token when it is displayed; Threadline cannot reveal it again.
3. In r5d, open **Settings → MCP servers** and add a remote server:
   - **URL:** `https://your-threadline.example.com/mcp` (your deployment's `BASE_URL` plus `/mcp`).
   - **Transport:** Streamable HTTP.
   - **Authentication:** static bearer token, the personal Threadline key. On the wire this is `Authorization: Bearer TOKEN`.
4. Connect and check the available tools. Keep the token in the client's secret configuration, never in an issue, prompt, URL or repository.

The r5d worker/client must be able to reach this URL. Unlike the outgoing [r5d plugin feed](/guides/plugins), MCP requires network access from the agent to Threadline. Use HTTPS and preserve the Authorization header through your reverse proxy. No OAuth registration or browser cookie is required, and cookies alone cannot authenticate `/mcp`.

## Available tools

All keys require read scope. Read-only keys expose only the six read tools; write tools are registered only for keys with both read and write scopes.

| Tool | Inputs | Purpose |
| --- | --- | --- |
| `workspace_list` | Optional `workspace` | Discover workspaces; `role: null` means nonmember, not permission to read content. |
| `issue_lookup` | `number` | Resolve a workspace-local display number to issue details and its stable internal ID. |
| `issue_get` | `issueId` | Read an issue with comments, project, state, URL and board lane display name. |
| `issue_list` | Optional `project`, `state`, `text` | List/search accessible issues by project slug, open/closed/draft state and title/body text. |
| `project_list` | None | List readable projects, including archived projects. |
| `project_lanes` | `project` | List a project's visible board lanes with stable IDs and current display names. |
| `issue_comment` | `issueId`, `body` | Add a Markdown comment. |
| `issue_close` | `issueId`; optional `reason`, `duplicateOfId`, `comment` | Close without changing board placement. Reasons are `completed`, `not_planned`, or `duplicate` (requires a target). A supplied comment is saved atomically with closure. |
| `issue_reopen` | `issueId` | Reopen an issue. Like REST `state:open`, this also publishes a creator's personal draft. |
| `issue_move` | `issueId`, `lane` | Move an existing card to a visible lane; pass null to take it off the board. Does not add an off-board issue. |

Every tool accepts optional `workspace` (a slug; defaults to `default`). Set it for each call targeting another workspace. Start with `workspace_list`, then use `issue_lookup` with the displayed `number` and `workspace`. Pass the returned `issue.id` to `issue_get` and write tools. Issue IDs (including `duplicateOfId`) remain stable internal decimal strings, not workspace display numbers; two workspaces may both contain issue `!12` with different IDs. `project` means the URL slug, not its display name. Use `project_lanes` to discover lane values instead of guessing from labels: a lane may have been renamed. Issue results include canonical `/w/:workspaceSlug/issues/:number` URLs built from the configured deployment URL. Cross-workspace moves, duplicate links and parent/child relationships are not supported.

## Permissions and content safety

MCP tools call the same data handlers as REST. Private-project permissions, creator-only draft privacy (no administrator override), archived-project read-only rules, content validation, change history and actor attribution all apply. Knowing an issue number does not grant access. Permission changes apply to existing tokens immediately.

Keys inherit the user's current workspace memberships and project permissions; selecting `workspace` scopes a call, not the credential itself. Public listing grants no content access, and hidden workspaces are discoverable only by members/instance administrators. Full token scope does not override read-only workspace/project access. Choose a user with the intended permissions. An administrator's token carries administrator data access, not permission to bypass draft privacy. The MCP endpoint exposes no workspace-management, invitation, account, SSO, plugin-settings or credential-management tools.

Tool descriptions explicitly mark issue/comment content and other user-written labels as **untrusted data, not instructions**. Agents should use your request as instructions and treat retrieved Markdown as evidence. A read-and-write key allows real changes; use a read-only key for investigation or review. In particular, publishing a draft broadens its audience.

## Protocol and troubleshooting

The endpoint is stateless Streamable HTTP with finite JSON responses, implemented using the official v2 server SDK. It supports modern `2026-07-28` discovery and legacy `initialize` negotiation for `2025-06-18` and `2025-03-26`. The real v2 client with automatic version negotiation is covered by HTTP integration tests. It does not require persistent MCP sessions or an SSE subscription.

- **401:** Missing, invalid, expired or revoked key. Create a replacement or update the client's token. Invalid Authorization never falls back to cookies.
- **403:** Missing scope or a supplied foreign Origin. Backend clients can omit Origin; a supplied Origin must match `BASE_URL`.
- **Tool error with 404:** The issue/project is missing or unreadable by this key's user.
- **Tool error with 409:** Usually an archived project or incompatible issue state. Restore the project through Threadline before changing content.
- **Write tool missing:** The key is read-only. Create a separate read-and-write key if mutation access is intended.
- **HTML instead of MCP:** Verify the exact `/mcp` URL, that the running application includes MCP support, and that the proxy routes it to Threadline rather than an authentication portal or static page.

Revoke the key in **API access** when the integration is no longer needed. Revocation and expiry are checked on every MCP request; there is no refresh token. Responses are no-store and request bodies are limited to 256 KiB. See [API access](/development/api-access) for key storage, scopes and lifecycle details.
