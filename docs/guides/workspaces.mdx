## Choose a workspace

Use the workspace switcher to select where you work. Lists, projects, boards, references, pins and issue creation are scoped to that workspace. Canonical routes begin with `/w/SLUG`: projects use `/w/SLUG/projects/PROJECT`, boards append `/board`, and issues use `/w/SLUG/issues/NUMBER`.

Each workspace has its own issue numbering. `!12` means issue 12 in the containing workspace, not issue 12 across the installation. Internal issue IDs remain globally stable keys for APIs and relationships; they are not display numbers. Moving between projects in the same workspace preserves both. Cross-workspace moves, parent/child relationships and duplicate links are not supported.

## Discovery is not access

**Public** workspaces are listed to signed-in users, but listing does not grant membership or access to projects/issues. **Hidden** workspaces appear only to their members and instance administrators. A discovered workspace with no membership has `role: null` in API results. Anonymous visitors do not gain application access through public listing.

## Member permissions

Workspace administrators manage membership and permissions. Instance administrators can manage every workspace. A workspace must retain at least one workspace administrator.

Each member has a default project access level:

- **None:** no default project access.
- **Read:** read-only access; no content, comment or board mutations.
- **Full:** collaborative writes, subject to archive and other data rules.

Specific projects can override the default with **Read** or **Full**. The specific value wins, rather than taking the greater permission: default Full plus project Read makes that project read-only; default None plus project Full grants access only there. Unlinked issues use the default access level. Workspace administrators have full workspace access. Creator-only personal drafts still have no administrator bypass.

New workspace memberships use these explicit defaults/overrides. Migrated Default memberships retain legacy private-project owner/sharing restrictions until explicitly converted with `convertLegacyAccess:true` (unchanged saves preserve legacy restrictions); this avoids broadening existing private content on upgrade. Member responses expose `legacyAccess` so administrators can identify this compatibility mode. Replacing it requires an explicit `convertLegacyAccess:true` member update; the UI warns and asks for confirmation because conversion may expose previously private projects. Merely opening permissions and saving unchanged does not convert it. Project visibility and sharing fields are not a substitute for configuring the new membership permissions.

## Invite and manage people

A workspace administrator invites an email address with a default access level and optional project overrides. Invitations are pending grants, not local-account creation or password-reset links. They are applied when the server can verify that the signed-in account owns the matching email. OIDC requires verified email; local accounts are provisioned by the instance administrator. Do not assume an email notification was sent: share the installation's sign-in instructions separately.

Pending invitations can be updated or revoked. Existing members are changed through member settings, not reinvited; invitations do not silently escalate an existing membership. Removing a member removes their workspace access, but cannot retract data already copied or downloaded. Membership edits replace the project-override list, so retain every override you intend to keep.

## Creation and instance administration

Instance administrators can create workspaces and see hidden ones. The instance setting **Allow user workspace creation** (initially enabled) (`allowUserWorkspaceCreation`) controls whether ordinary signed-in users can create them too. A creator becomes the workspace administrator with Full access. Choose a unique lowercase hyphenated slug at creation; renaming the workspace does not change its slug. Workspace name and public/hidden listing can be edited afterward.

Workspace management, invitations and this instance setting require a browser session. API keys, even write keys, cannot administer them. Read keys may discover workspaces with `GET /api/workspaces`. See [API access](/development/api-access), [CLI](/guides/cli) and [MCP](/guides/mcp) for scoped integration calls.

## Upgrade to Default

The migration creates **Default** (`default`) and places existing projects/issues there, keeping internal IDs, display numbers, content, comments, boards and relationships. Existing users retain compatible Default membership; existing private-project restrictions and draft privacy are preserved. New workspaces have independent number sequences. Pending Default invitations take precedence: invited accounts receive the invitation’s configured access after email verification, not automatic Full access. For compatibility, new accounts without a pending Default invitation join public Default with legacy Full access; making Default hidden stops this ordinary-account automatic onboarding. Other workspaces require explicit membership/invitations. Review Default's visibility and membership when onboarding through local accounts or SSO. Update bookmarks/integrations to canonical workspace-prefixed routes, and distinguish display numbers from stable IDs.

Back up the complete data directory before upgrading. Rollback requires restoring the matching pre-upgrade backup, not simply running an older application against the migrated database.
