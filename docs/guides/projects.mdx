Projects group related issues into a list and a board.
Use a project for a product, a team initiative, or a clearly scoped body of work.

<Note>
  Select a [workspace](/guides/workspaces) first. Membership defaults and project Read/Full overrides control access. Public workspace listing does not grant content access. Unlinked issues use the member's default access.
</Note>

## Manage access

New projects belong to their creator. Configure workspace membership defaults and project-specific overrides for the intended audience. Legacy project visibility/owner/sharing fields remain available; migrated Default memberships retain private-project owner/sharing restrictions until explicitly converted with `convertLegacyAccess:true` (unchanged saves preserve legacy restrictions). Only authorized owners/administrators can change project access settings.

Full access permits collaborative writes to active project details, issues and boards, and archive/restore. Read access is read-only, even when an API key has write scope. Comment editing and deletion still require the comment author or an administrator. Tagging someone does not share a private project with them.

Users who lose access stop seeing the project in lists, pins, issue references, and move destinations. Direct project, issue, comment, and history routes return not found. Saved pins return if access is restored. Attachments follow current issue access, including references retained in history.

On upgrade, existing projects remain public. Their owner is the earliest administrator by creation time, then user ID; if no administrator exists, the owner stays unset until an administrator assigns one. Existing shared-user lists start empty.

## Create a project

1. Sign in and open **Projects**.
2. Select **Create project**, or **Create your first project** in an empty workspace.
3. Enter a **Project name**, such as `Website redesign`.
4. Add an optional **Description** explaining the goal and scope.
5. Review project visibility/sharing and the workspace membership defaults and overrides; listing or visibility alone is not a membership grant.
6. Select **Create project** to open the new project's issue list.

Project creation requires Full default workspace access or workspace/instance administration privileges.
You can change the name and description later using **Edit project**.

| Field | Limit | Suggested content |
| --- | --- | --- |
| Project name | Required; up to 100 characters | A short, recognizable initiative name |
| Description | Up to 10,000 characters | Purpose, scope, and what belongs here |

The project URL is `/w/WORKSPACE/projects/PROJECT`, using a generated project slug derived from the name plus a random suffix.
You do not need to choose or manage that slug yourself.
Copy the browser URL when directing teammates to the project.
Recipients must sign in and have project access to see its data.

## Edit a project

Open the project's **List** or **Board**, select **Edit project**, then update its name or description and choose **Save changes**. To change only the name, open the project's **⋮** menu in the sidebar and choose **Rename project**. The name is required; the description can be cleared. Members with Full access can edit an active project.

Renaming keeps the project's URL, issue links, board, and history unchanged. The sidebar and project cards show the saved name immediately. Canceling a changed draft asks before discarding it, and a failed save keeps your draft for retry. Editing project details never saves or discards unsaved issue edits in the side panel.

Archived projects remain read-only. Select **Restore project** before editing their details.

## Read the project overview

Each project card shows its name, description, visibility, owner, shared-user count, unfinished board work, and total issue count. Administrators see every project, including private projects they do not own.
Unfinished work counts open issues on the board outside the built-in **Done** lane, including cards in hidden lanes.
Closing an issue or moving its card to **Done** reduces that count without deleting anything.
Issues that are not on the board count only toward the total.

<Tip>
  Keep the description focused on the project's purpose.
  Put changing implementation details and discussion in issues, where teammates can update them.
</Tip>

## Pin projects

Hover over a project in the sidebar, or focus it with the keyboard, to show its **⋮** menu. Choose **Pin project** to add it to **Pinned projects**, and use **Move up**, **Move down**, or **Unpin project** from a pinned project's menu. You can also drag pinned projects to rearrange them, drag other projects into the pinned list, or drag a pin back to **Projects**. Project cards on the projects page keep a pin button. The pinned section is hidden while you have no pins.

Pins and their order are personal to your signed-in account and follow you across devices. Other sidebar projects are ordered by their most recently updated issue, newest first; projects without issues use their creation time. Archiving hides a pin without forgetting it, so restoring the project brings it back. Favorites from earlier versions become pins automatically.

## Start organizing work

Open a project card, then select **Create issue** to add the first task.
Issues receive workspace-local numbers across its projects and unlinked issues, shown as `!1`, `!2`, and so on.
Use `!12` in an issue or comment to link to that issue, or share its `/w/WORKSPACE/issues/12` URL.

Use **List** to scan issues; it starts with a **State is Open** filter that you can edit or remove.
Use **Board** to plan selected work in lanes; see [the board guide](/guides/board).
Both views offer title, number, and label search.
Neither view creates a separate copy of the project's issues.

## Archive a project

Archive a project when its work is finished but you want to keep it for reference.

1. Open the project, or open its **⋮** menu in the sidebar.
2. Select **Archive** (or **Archive project** in the menu), then confirm with **Archive project**.

Archived projects leave the sidebar and the default project list.
Find them under **All projects** by selecting **Archived**.
They stay readable, including issues, comments, and the board, but are read-only: nobody can create or edit issues, close or reopen them, comment, or change the board.
Open issues stay open; archiving does not close them.

To work in the project again, open it and select **Restore project**.
Members with Full access can archive or restore a project.

## Plan for retained projects

The current release has no project delete action.
Issues can move between active projects with Full access in the same workspace or become **No project** issues when default workspace access permits. Cross-workspace moves are not supported. Moving changes the audience of their content, comments, history, and attachments; unlinking makes them workspace-wide.
Create projects deliberately rather than treating them as disposable folders.

When work finishes, close its issues and archive the project to keep it as a reference.
Use workspace membership defaults and project overrides for restricted work. Administrators retain access, and already-downloaded or copied information cannot be retracted.
Review [current limitations](/admin/limitations) before inviting a broader audience.
