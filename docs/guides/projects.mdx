Projects group related issues into a list and a board.
Use a project for a product, a team initiative, or a clearly scoped body of work.

<Warning>
  Every project is shared with every authenticated user.
  There are no project memberships, private projects, or per-project access controls.
  A project is an organizational boundary, not a security boundary.
</Warning>

## Create a project

1. Sign in and open **Projects**.
2. Select **Create project**, or **Create your first project** in an empty workspace.
3. Enter a **Project name**, such as `Website redesign`.
4. Add an optional **Description** explaining the goal and scope.
5. Select **Create project** to open the new project's issue list.

Any authenticated member can create a project; administrator access is not required.
You can change the name and description later using **Edit project**.

| Field | Limit | Suggested content |
| --- | --- | --- |
| Project name | Required; up to 100 characters | A short, recognizable initiative name |
| Description | Up to 10,000 characters | Purpose, scope, and what belongs here |

The project URL uses a generated slug derived from the name plus a random suffix.
You do not need to choose or manage that slug yourself.
Copy the browser URL when directing teammates to the project.
Recipients must sign in to access its data.

## Edit a project

Open the project's **List** or **Board**, select **Edit project**, then update its name or description and choose **Save changes**. The name is required; the description can be cleared. Any signed-in member can edit an active project.

Renaming keeps the project's URL, issue links, board, and history unchanged. The sidebar and project cards show the saved name immediately. Canceling a changed draft asks before discarding it, and a failed save keeps your draft for retry. Editing project details never saves or discards unsaved issue edits in the side panel.

Archived projects remain read-only. Select **Restore project** before editing their details.

## Read the project overview

Each project card shows its name, description, unfinished board work, and total issue count.
Unfinished work counts open issues on the board outside the built-in **Done** lane, including cards in hidden lanes.
Closing an issue or moving its card to **Done** reduces that count without deleting anything.
Issues that are not on the board count only toward the total.

<Tip>
  Keep the description focused on the project's purpose.
  Put changing implementation details and discussion in issues, where teammates can update them.
</Tip>

## Start organizing work

Open a project card, then select **Create issue** to add the first task.
Issues receive globally unique numbers across every project and unlinked issue, shown as `!1`, `!2`, and so on.
Use `!12` in an issue or comment to link to that issue, or share its `/issues/12` URL.

Use **List** to scan **Open** or **Closed** issues.
Use **Board** to plan selected work in lanes; see [the board guide](/guides/board).
Both views offer title, number, and label search.
Neither view creates a separate copy of the project's issues.

## Archive a project

Archive a project when its work is finished but you want to keep it for reference.

1. Open the project.
2. Select **Archive**, then confirm with **Archive project**.

Archived projects leave the sidebar and the default project list.
Find them under **All projects** by selecting **Archived**.
They stay readable, including issues, comments, and the board, but are read-only: nobody can create or edit issues, close or reopen them, comment, or change the board.
Open issues stay open; archiving does not close them.

To work in the project again, open it and select **Restore project**.
Any signed-in member can archive or restore a project.

## Plan for retained projects

The current release has no project delete action.
It also does not expose an issue move between projects.
Create projects deliberately rather than treating them as disposable folders.

When work finishes, close its issues and archive the project to keep it as a reference.
Do not use project organization to separate information that different users must not see.
Review [current limitations](/admin/limitations) before inviting a broader audience.
