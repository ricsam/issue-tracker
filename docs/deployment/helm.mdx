The standard Helm repository is `https://ricsam.github.io/issue-tracker`. This guide targets chart **0.16.0**. A chart version and an application image tag are separate choices.

## Prerequisites

Have Helm 3, kubectl access to your chosen namespace, a provisioner or existing RWO claim, and a final HTTPS origin. Your ingress controller, DNS, and TLS certificate are operator-managed.

```sh
helm repo add issue-tracker https://ricsam.github.io/issue-tracker
helm repo update
helm search repo issue-tracker --versions
```

Verify `0.16.0` is listed before installing. Pinning the chart version keeps later releases from changing this install. Version 0.16.0 adds configurable table-column visibility/order with per-account browser preferences and fixes mobile table hit areas that can intercept scrolling or Board navigation on older Safari versions. No database migration, API change, or deployment-value change is added by this release.

When upgrading from before 0.15.0, issue history, personal project favorites, and strict lowercase kebab tags such as `#needs-review-2` are also included. Uppercase, Unicode, underscores and bracketed tags are no longer recognized; invalid tag text remains ordinary prose.

Migration v12 adds history and favorites tables without inventing historical events. Migration v13 rebuilds the derived tag index without changing bodies, titles, timestamps or lifecycle; unsupported tags disappear from filters and suggestions. Back up `/data` and preserve the encryption-key Secret before upgrading. Avoid application-only rollback: older versions use different tag rules and do not maintain history. Restore a matching backup if recovery is necessary. Existing deployment values remain valid; publishing a chart does not upgrade running deployments.

When upgrading from before 0.12.0, migration v11 runs once transactionally, replacing UUID issue IDs with global sequential numbers in creation order while preserving content, comments, tagged users, lifecycle, timestamps and board membership/order. API issue IDs are now canonical positive decimal strings; `Issue.number` is their numeric equivalent. **Old UUID issue URLs are not supported.** Other entity IDs remain UUIDs, and historical prose is not rewritten. Back up all of `/data` and retain the encryption-key Secret before upgrading. **Do not use automatic Helm rollback (`--atomic`) across this migration:** older images cannot safely use the new issue IDs. Recovery requires the pre-upgrade backup with its matching image/chart, preserving newer writes separately first. Existing deployment values remain valid.

## Choose the image

CI publishes `ghcr.io/ricsam/issue-tracker:main` and `sha-...` tags after verification succeeds. Choose the `sha-...` image matching the chart release's source commit after its CI succeeds; `main` moves with successful CI. The chart intentionally has **no default tag** and does not use its `appVersion` as an image tag.

```sh
export IMAGE_TAG='<published-sha-tag-matching-the-release>'
docker manifest inspect "ghcr.io/ricsam/issue-tracker:$IMAGE_TAG" >/dev/null
```

Pin the confirmed SHA tag for a repeatable deployment. For a private replacement image, configure `imagePullSecrets` separately.

## Create the encryption-key Secret

```sh
kubectl create namespace issue-tracker
openssl rand -base64 32 | tr -d '\n' | \
  kubectl -n issue-tracker create secret generic issue-tracker-settings \
    --from-file=SETTINGS_ENCRYPTION_KEY=/dev/stdin
```

The Secret value is canonical base64 text decoding to exactly 32 bytes. Kubernetes applies its own storage encoding; `--from-file` handles that layer for you. Preserve this key securely with your backups. Do not commit a Secret manifest containing its value.

## Install without public ingress

```sh
helm upgrade --install issue-tracker issue-tracker/issue-tracker \
  --version 0.16.0 --namespace issue-tracker \
  --set-string image.tag="$IMAGE_TAG" \
  --set-string baseUrl=https://issues.example.com \
  --set-string existingSecret=issue-tracker-settings
```

<Warning>
Leave ingress disabled until [private administrator setup](/admin/setup) succeeds. A new unclaimed instance can be claimed by the first visitor who reaches setup.
</Warning>

The chart fixes the Deployment at **one replica**, uses **Recreate**, and mounts `/data` without subpaths. It runs as UID/GID 1000 with `fsGroup: 1000`, a read-only root filesystem, and a writable temporary directory. Service-account token mounting is disabled.

## Add ingress after setup

Keep all deployment-specific values in one non-secret file, for example `production-values.yaml`:

```yaml
image:
  tag: "<published-sha-tag-matching-the-release>" # Use the same tag as IMAGE_TAG.
baseUrl: https://issues.example.com
existingSecret: issue-tracker-settings
persistence:
  size: 5Gi
  storageClass: ""
ingress:
  enabled: true
  className: nginx # Replace with your controller's class.
  hosts:
    - host: issues.example.com
      paths:
        - path: /
          pathType: Prefix
  tls:
    - secretName: issues-example-tls
      hosts:
        - issues.example.com
```

```sh
helm template issue-tracker issue-tracker/issue-tracker \
  --version 0.16.0 --namespace issue-tracker -f production-values.yaml
helm upgrade issue-tracker issue-tracker/issue-tracker \
  --version 0.16.0 --namespace issue-tracker -f production-values.yaml
```

## Storage and resources

| Value | Default | Meaning |
| --- | --- | --- |
| `persistence.storageClass` | `""` | Omit `storageClassName`, using the cluster default |
| `persistence.size` | `1Gi` | Requested capacity for a new claim |
| `persistence.existingClaim` | `""` | Reuse this claim instead of creating one |
| `persistence.accessMode` | `ReadWriteOnce` | SQLite single-instance storage |
| `resources.requests` | `100m` CPU, `128Mi` memory | Scheduling requests |
| `resources.limits` | `500m` CPU, `512Mi` memory | Container limits |
| `existingSecretKey` | `SETTINGS_ENCRYPTION_KEY` | Key within the existing Secret |

A chart-created PVC carries `helm.sh/resource-policy: keep`. Do not override that annotation. An existing claim is never created or deleted by the chart. Neither retention nor RWO is a backup or protection against manual deletion.
