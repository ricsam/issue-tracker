# Threadline API contract

API responses are JSON except redirects/file downloads; errors `{ error: string }`. Data objects use `shared/types.ts`; credentials use `shared/api-access.ts`. Data routes accept session cookies or `Authorization: Bearer TOKEN`. Cookie-authenticated unsafe methods require a same-origin `Origin` header; valid bearer writes may omit it but reject a foreign supplied Origin. Auth cookies are HttpOnly, SameSite=Lax, and Secure in HTTPS. Administration and key management require browser sessions; runtime OIDC configuration also requires admin. Body content is canonical Markdown, not HTML.

## Workspace scope and identity

Data requests select a workspace with `X-Workspace-Slug: SLUG`; omission selects the saved initial workspace's slug (the workspace with internal ID `default`) for compatibility. That slug is `default` only with the default migration configuration; a custom initial slug is preserved and used instead. This scope applies to projects, issues, boards, comments, references, pins and uploads, including requests containing globally stable IDs. An ID never grants cross-workspace access. `Project` and `Issue` include `workspaceId` and `workspaceSlug`.

`Issue.id` is a stable globally unique decimal-string internal key. `Issue.number` is a workspace-local display number and is **not** an alias of the ID. Resolve a number with `GET /api/issues/by-number/:number` (returns `IssueDetail`) under the selected workspace; use the returned `issue.id` for mutations and relationships. Browser issue URLs are `/w/:workspaceSlug/issues/:number`. Project slugs and issue numbers are interpreted within one workspace. Cross-workspace moves, parent/child relationships and duplicate links are not supported.

`GET /api/workspaces` returns `{workspaces}` for authenticated discovery, including read-scope API keys. Public listing does not grant membership or content access; a discoverable nonmember workspace has `role: null`. Hidden workspaces are visible only to members and instance administrators. Workspace management and invitations require browser sessions, not API keys. Membership uses workspace default project access `none`, `read`, or `full`; a specific project `read`/`full` override wins over that default. Read-only access cannot mutate content, comments or boards. Creator-only drafts and archive restrictions still apply. Migrated Default memberships retain legacy private-project owner/sharing restrictions until explicitly converted with `convertLegacyAccess:true`; unchanged saves preserve legacy restrictions. New or explicitly converted memberships use defaults and overrides. See [Workspaces](guides/workspaces.mdx) for membership, invitations and administration.

Upgrading places existing projects and issues in **Default** (slug `default`) unless an initial name/slug was configured before migration 22 first ran. The initial workspace's internal ID remains `default` regardless of its slug; internal issue IDs, existing display numbers, content and relationships are preserved. Later restarts do not rename the saved workspace. New workspaces have independent numbering. Back up the complete data directory before upgrading; rollback requires restoring the matching backup, not running old code on the upgraded database.

Except discovery, these routes require browser sessions; writes require same-origin Origin. Workspace management requires workspace or instance administration. Discovery also returns `allowUserWorkspaceCreation` alongside `workspaces`.

`WorkspaceMember.legacyAccess` indicates preserved legacy private-project owner/sharing restrictions. Member PATCH preserves that mode unless `convertLegacyAccess:true` explicitly requests replacement by defaults/overrides; an unchanged save never converts it. Conversion can broaden access to previously private projects, so the UI warns and requires confirmation.

Invitations match server-verified account email and are applied automatically; they do not create accounts or send a credential. Reinviting an existing member returns 409; use member PATCH. Pending invitations for the same workspace/email are updated rather than duplicated. The migration enables user workspace creation initially. Pending Default invitations take precedence over compatibility onboarding: their configured grants apply after email verification, without an automatic Full grant. Only accounts without a pending Default invitation receive public Default legacy Full access; hidden Default and other workspaces require explicit membership/invitations (instance admins retain administrative access).

## API keys and CLI authorization

See [API access](development/api-access.mdx) for the complete protocol and [CLI](guides/cli.mdx) for commands. Personal keys have `read` or `read` + `write`, inherit current user permissions (including private projects/drafts), expire after 1–365 days, and are revocable. Only a SHA-256 hash is stored. Browser-issued CLI keys last 90 days. Invalid bearer headers never fall back to cookies. All responses are no-store. Keys cannot use administration/auth/key-management endpoints; their sole credential mutation is self-revocation.

| Method | Route | Request and response |
| --- | --- | --- |
| GET | `/api/me` | `{user,key}`; key metadata for bearer auth, null for session |
| DELETE | `/api/me/token` | Bearer only, including read-only keys → `{ok:true}`; revokes the current token |
| GET | `/api/me/api-keys` | Session only → `{keys:ApiKeyInfo[]}`; only the current user's metadata |
| POST | `/api/me/api-keys` | Session + Origin; `{name,scopes,expiresInDays}` → `{key,token}`; token revealed once |
| DELETE | `/api/me/api-keys/:id` | Session + Origin → `{ok:true}`; own key only, idempotent |
| POST | `/api/auth/device/code` | Public JSON `{name,scopes}` → `{deviceCode,userCode,verificationUri,verificationUriComplete,expiresIn:600,interval:5}` |
| GET | `/api/auth/device/request?user_code=ABCD-EFGH` | Session only → `{userCode,name,scopes,expiresAt,tokenExpiresInDays:90}`; pending requests only |
| POST | `/api/auth/device/approve` | Session + Origin; `{userCode,approve:boolean}` → `{ok:true}`; explicit single decision |
| POST | `/api/auth/device/token` | Public JSON `{deviceCode}` → `{accessToken,tokenType:"Bearer",key,user}`; single-use exchange |

Device POSTs may omit Origin, but require JSON and reject foreign supplied Origin. Pending/denied/expired/too-frequent polls return HTTP 400 with `error` equal to `authorization_pending`, `access_denied`, `expired_token`, or `slow_down`. Increase the poll interval by five seconds on slow_down. Both codes are hashed at rest. Names are unverified and approval must compare the code from the user's own terminal. No GET approves and no bearer token may approve. Login and device starts have separate 20/minute direct-peer budgets; reviews/approvals use 20/minute per account (anonymous requests: peer). Valid polls use per-code pacing; invalid/expired polls use a separate 120/minute peer budget. Forwarded headers are not trusted. Device bodies are capped at 4 KiB. Migration 18 adds these tables without changing existing sessions/content. Offline admin recovery revokes that admin's keys and approved pending grants; web logout does not revoke keys.

OIDC login accepts only `/new`, `/cli/authorize`, or `/cli/authorize?user_code=ABCD-EFGH` as allowlisted `returnTo` values; everything else returns to `/`.

## Plugins

Migration 19 adds `plugin_settings` (enabled flag, non-secret JSON, AES-256-GCM encrypted secret fields), `plugin_links` (unique plugin/issue/external ID, title, HTTP(S) URL, nullable status, tone) and `plugin_state` (plugin/key JSON). It changes no existing issue content, timestamps, board placements or credentials. Back up `DATA_DIR` and the settings encryption key before upgrading; restore the backup for rollback.

| Method | Route | Request and response |
| --- | --- | --- |
| GET | `/api/admin/plugins` | Admin browser session → `{plugins:PluginAdminSettings[]}`; declarative fields, values, secret-presence flags and task status; no secrets |
| PUT | `/api/admin/plugins/:id` | Admin session + Origin; `{enabled:boolean,values:Record<string,unknown>}` → `{plugin:PluginAdminSettings}`; validate/check before saving, empty/omitted secret preserves |
| GET | `/api/plugins` | Signed-in browser → `{plugins:PluginPublicSettings[],baseUrl:string}`; enabled plugins' explicitly public non-secret settings, project mappings filtered by project access; canonical deployment origin |
| GET | `/api/issues/:id/external-links` | Data auth → `{links:ExternalLink[]}`; identical issue/draft/private-project authorization to issue details |

`Issue.externalLinks` contains the same links in detail and list responses. Disabled-plugin links are hidden. `ExternalLink` has `pluginId`, `externalId`, `title`, `url`, nullable `status`, and `tone` (`neutral`, `info`, `success`, `warning`, `danger`). Links are plugin-owned; there is no client write endpoint. URLs must use HTTP(S) without credentials. A known external ID or URL never grants issue access. Admin keys cannot bypass creator-only drafts.

The compiled registry lives in `shared/plugins.ts`; server definitions/runtime in `server/plugins/`, browser actions in `src/plugins/`. Fields support text, URL, select, secret and per-project tables. Plugins can expose selected public fields, validate settings, subscribe to post-commit issue created/updated/closed/reopened, comment created and card moved hooks, and run abortable background tasks with isolated key-value state. No runtime third-party code loading. Failed hooks/tasks are logged without secret details and cannot fail content requests. Settings changes restart tasks; disabling or shutdown aborts them. No-op/failed content mutations emit no hooks.

The r5d plugin uses only the configured service base URL, rejects redirects and requires HTTPS (HTTP localhost only under the existing non-production insecure-OIDC localhost option). Saving enabled settings checks `GET /api/v1/teams/:team`. Its secret team key never goes to the browser. A fresh feed lists sessions before polling events with `wait=30` and a 45-second fetch timeout; cursors and deduplication state are durable, newer status versions win, and expired cursors reconcile from a fresh list. Revocation removes links; review-request events associate pull requests with the sessions' issues. Only top-level sessions with `source:threadline` work items naming this deployment's canonical `/w/:workspaceSlug/issues/:number` produce links. 401/404 stops polling and reports an admin error; transient errors back off. Browser launch links use the strict r5d version-1 deflated/base64url fragment format, bounded saved issue/comment snapshots and optional mapped remote/branch/sharing. See [the guide](guides/plugins.mdx).

## MCP

`/mcp` is a stateless Streamable HTTP endpoint using the official v2 server SDK and finite JSON responses. It supports modern `2026-07-28` discovery and legacy `initialize` (`2025-06-18` / `2025-03-26`). Authentication is **personal API key bearer only**, never browser cookies. Every request rechecks key expiry/revocation and rejects a supplied foreign Origin. Responses are no-store; request bodies are capped at 256 KiB. Keys have the same data access as REST, not plugin administration rights.

Read scope exposes `workspace_list`, `issue_lookup`, `issue_get`, `issue_list`, `project_list`, `project_lanes`. All tools accept optional `workspace` (slug, default `default`). `workspace_list` discovers workspaces; `issue_lookup` takes a workspace-local `number` and resolves its stable ID. Read plus write also exposes `issue_comment`, `issue_close`, `issue_reopen`, `issue_move`. `issue_get` takes a stable internal decimal-string `issueId`, not a display number; all other `issueId`/`duplicateOfId` inputs also remain stable internal IDs; list filters are optional `project` slug, `state` (open/closed/draft) and `text`; `project_lanes` takes `project`; commenting takes `issueId,body`; close/reopen take `issueId`; close additionally accepts optional `reason`, `duplicateOfId`, and `comment` (the atomic close endpoint below); move takes `issueId,lane` (stable lane ID or null for removal). Move operates on an existing card, not off-board issue placement. Results include canonical issue URLs and current lane display names. Tool descriptions mark content as untrusted data. Tool failures use MCP `isError` results; authentication fails at HTTP 401 and foreign origins at 403. REST handlers enforce project/draft/archive permissions, content validation, attribution and history for every tool. See [MCP setup](guides/mcp.mdx).

## Sub-issues

Migration 20 transactionally adds `issue_relationships` (one parent per child, indexed parent lookup, foreign keys and a self-link check). Startup is idempotent and preserves all existing data. Back up the data directory before upgrading; rollback requires restoring that backup.

`GET /api/projects/:slug/board/sub-issue-progress` returns `{progress:Record<string,SubIssueProgress>}`, where `SubIssueProgress` is `{total:number,closed:number}`. Only currently readable published parents on that project's board with at least one currently readable published direct child are included; leaves and parents with only inaccessible children have no entry or zero placeholder. Children may be off-board, in another readable project, or unlinked; descendants beyond direct children are not counted. `closed` counts non-null `closedAt`, independently of board lanes. Hidden-lane parents remain included for client display filtering. Permissions for the project, parents and children are rechecked on each read, including after moves or sharing revocation. Readable archived boards are supported. Session and read-scope bearer authentication are accepted; anonymous requests return 401 and missing/inaccessible projects return 404. This read-only aggregate exposes no child IDs, titles or credentials and requires no migration.

- `GET /api/issues/:id/relationships` → `IssueRelationships` directly: `{parent: IssueReference|null, subIssues: IssueReference[]}`.
- `POST /api/issues/:id/sub-issues` with `{issueId:string}` attaches an existing child and returns the parent's `IssueRelationships`.
- `DELETE /api/issues/:id/sub-issues/:childId` detaches that pair and returns the parent's `IssueRelationships`.
- Both issue creation routes additionally accept `parentId?:string`. Creation and attachment are atomic; failure leaves no issue, board placement or history behind. Existing create response shapes are unchanged.

References contain only `{id,number,title,state}`. Children are ordered by numeric ID. All IDs use canonical decimal strings. Reads authorize the requested issue and filter every related endpoint against current permissions; hidden parents appear as null and hidden children are omitted without counts or placeholders. Relationships are not embedded in issue lists/details.

Mutations require full access and active (unarchived) projects for both endpoints. Draft endpoints are rejected (409; inaccessible drafts return 404). Closed and cross-project published issues within the same workspace are supported; cross-workspace relationships are rejected. Nesting is allowed; self-links, cycles and a different existing parent return 409. The existing-parent conflict is generic even if that parent is hidden or archived; remove it explicitly with access to both endpoints (and restore archived projects first). No old parent metadata is returned. Attaching the same pair and detaching an absent pair are idempotent after authorization; neither silently reparents. Missing/inaccessible endpoints return 404, malformed inputs 400, anonymous requests 401, and read-only bearer mutations 403.

Moves, access revocation, archive/restore and close/reopen preserve relationships without cascading lifecycle changes. Link changes do not write text history or copy related IDs/titles into another issue's history. This deliberately avoids durable cross-project disclosure after later access changes. Existing issue history is otherwise unchanged. Cookie CSRF and bearer read/write scopes apply as for other data routes.

## Project and attachment authorization

`Project` includes `visibility:"public"|"private"`, `ownerId:string|null`, and `sharedUserIds:string[]`. Public project visibility is evaluated inside the selected workspace's membership and project-access rules, never as anonymous or cross-workspace access. For legacy Default memberships, private projects require owner/sharing access or administration privileges. New or explicitly converted memberships instead use workspace defaults and explicit project overrides. Published unlinked issues remain workspace-wide. Personal drafts additionally require creator identity, with no administrator or project-owner exception. All direct project/issue/comment/history routes and every mutation enforce this boundary; inaccessible targets return 404. Lists, board maps, references, and pins omit inaccessible data. Full project access permits collaboration; read-only members cannot change metadata, archive/restore, issue content or boards. Access administration still requires the relevant owner/administrator authority. Comment edit/delete still additionally require author/admin privileges.

Access PATCH accepts a nonempty subset of `visibility`, `ownerId`, and `sharedUserIds` only. Visibility must be public/private; ownerId must identify an existing non-null user; shares must be unique existing user IDs (an empty array revokes all shares). Unknown fields and invalid users return 400 atomically. Only owner/admin may change these settings (403 for another readable-project member, 404 for an inaccessible project). Archived access settings may change without restoring the project. Creation accepts optional visibility and shares with the same validation, always assigns the session user as owner, and rejects caller-supplied ownerId. Same-origin CSRF protection applies.

Moving issues requires source and destination access, in addition to active-project checks. Mixed bulk operations containing inaccessible issues fail and roll back all changes and history. References/mentions/URLs do not grant access. Moving a published issue to a public project or unlinking it broadens its audience, including comments, history and attachments. Drafts remain creator-only when moved.

Unsaved uploads are readable by the uploader and administrators. Once referenced by a saved issue, there is no administrator bypass; references only from another user's drafts do not grant download access. Saved references in issue bodies, comments, or retained history inherit that issue's current visibility dynamically. Any readable referencing issue grants download access; a known URL alone does not. Saving inaccessible attachment URLs is rejected with 404 rather than granting access through a newly saved reference. Once saved references exist, uploader identity alone no longer bypasses their access boundary. Removing a current link or deleting a comment does not revoke access while readable history retains the reference. Legacy referenced uploads use the same rule; legacy unreferenced uploads are administrator-only. Inaccessible downloads return 404 and anonymous downloads 401. Raster/download safety headers remain unchanged.

Migration v14 adds access state without privatizing existing projects: public visibility, empty sharing, and the earliest administrator by createdAt then id as owner (null when none exists). It preserves project content, lifecycle, issues, history and favorites. Normal startup upgrades to 14; `openDatabase(path, 13)` remains available for pre-migration fixtures. Back up the complete data directory before upgrading; rollback requires restoring a pre-upgrade backup.

Pins (formerly favorites) are stored per authenticated user, never on the shared `Project` object. PUT/DELETE require same-origin protection and use the session user only; a body cannot select another user. `/api/me/pinned-projects` returns readable pins in saved order. PUT without `beforeProjectId` appends an unpinned project and leaves an existing pin in place; `beforeProjectId:null` moves the project to the end, and a pinned project ID moves it immediately before that pin. Using the project itself or an unpinned target returns 400; unknown or inaccessible projects, including targets, return 404. Each write updates the complete order atomically, including archived or temporarily inaccessible pins. The legacy favorites routes remain for older clients: they return the same readable pins sorted by project ID and ignore request bodies. Revocation filters pins without deleting them; restored access makes them visible again. Archived projects can be pinned/unpinned, and archiving never deletes pins; clients hide archived pins until restoration.

`Project.lastIssueUpdatedAt` is the latest `updatedAt` among issues currently belonging to the project that the requesting user can see, or null when it has none. The sidebar orders unpinned projects by it, newest first, using `createdAt` when null.

Migration v15 adds a per-user pin position to the favorites table, initialized in each user's previous project-ID order, plus indexes for pin order and per-project issue activity. It keeps every existing favorite, including archived or inaccessible projects, and does not change issues, comments, or history. Normal startup upgrades through migration 15; earlier target versions remain available for migration fixtures. Back up the complete data directory before upgrading; rollback requires restoring a pre-upgrade backup.

Issue history is authenticated and readable for archived projects. `IssueHistoryEntry` contains `id:number`, `issueId:string`, `actorId:string`, `createdAt:string` (ISO timestamp), `action` (`created`, `updated`, `commented`, `comment_edited`, `comment_deleted`), and `changes` (`{field,before,after}[]`). Fields are `body`, `state`, `closeReason`, `project`, `boardLane`, or `comment`; values are string or null. Bodies/comments retain complete Markdown snapshots, state is draft/open/closed, and project/lane values snapshot readable names (null means no project/not on board). Creation records initial non-null values with null before; subsequent combined edits are one event per changed issue. Identity changes between equally named projects still record an event. All board membership routes record additions/removals/lane changes; ordering alone, lane visibility/order, project renaming, and no-op writes do not. Bulk body labels/mentions record body changes. Comments record their create/edit/delete snapshots. Events commit in the same transaction as mutations; failed writes cannot leave events. Pagination orders by history ID descending, not timestamp; `before` is an exclusive positive safe-integer decimal cursor. `limit` defaults to 50 and accepts 1–100; invalid cursors/limits return 400. Missing/malformed issue IDs return 404. Fetch the next page using the last returned event ID; `hasMore` is computed using one extra row.

Migration v12 additively creates history and user/project favorite tables and a history pagination index. It never backfills fictional pre-upgrade events, truncates saved history, or resets favorites. Historical migration fixtures may still request targetVersion 10 or 11; normal startup now upgrades through migration 15.

Project metadata PATCH requires at least one of `name` (trimmed, 1–100 characters) or `description` (0–10,000 characters, empty clears it). Omitted fields are preserved. Unknown keys, empty payloads and combining metadata with `archived` return 400. Any authenticated member with full project access may edit an active project, with same-origin CSRF protection; archived metadata edits return 409 until restored separately. Updates are transactional and preserve `id`, `slug`, `createdAt`, lifecycle fields, counts, issues, comments and board configuration/membership. Renaming never changes existing URLs.

Issue content is a single Markdown `body` (maximum `ISSUE_BODY_MAX_LENGTH = 101000` characters). Body-only POST/PATCH requires non-whitespace content. `Issue.title` remains a derived display cache: first ATX/setext heading outside fenced/indented code, otherwise the first meaningful text line, with common inline markup/links removed and a 300-character maximum; image/code-only content displays `Untitled issue`. `deriveIssueTitle` is exported by `shared/issue-content.ts`. State-only and project-only PATCH preserve content and cache. For legacy clients, optional nonempty `title` (max 300) is merged into the body as an escaped leading heading on POST or PATCH with body; an equivalent existing leading heading is not duplicated. Title-only PATCH replaces/adds the leading heading and preserves the remainder. The final merged body must fit the body limit. SQLite migration v3 transactionally prepends each old title as an escaped heading (unless an equivalent heading already leads the body), preserving original body bytes and all timestamps/metadata, and recomputes the title cache. Migration runs once, safely across reopenings.

`Lane` is a string ID. Built-in `LANES` are `todo`, `in_progress`, and `done`, labelled Todo, In progress, Done in that default order. `BoardLane` is `{value:Lane,label:string}`, `BoardCard` is `{issueId:string,lane:Lane}`, and `BoardSettings` is `{lanes:Lane[],customLanes:BoardLane[],cards:BoardCard[]}`. Cards include all explicitly selected work, even in hidden lanes. Each lane's subsequence in the cards array defines its persisted display order; clients must not re-sort by issue number. Cards expose no position field. New boards default to all three visible lanes, no custom definitions and no cards. PATCH board accepts nonempty unique known `lanes` and optional `customLanes`, stores `lanes` in the submitted order (the board's left-to-right display order), and never touches cards. Custom definitions are project-specific, merged additively and immutable: IDs must be lowercase `custom_<UUID v4>`, labels are trimmed to 1–60 characters and unique case-insensitively including default names, and there may be at most 30 custom definitions. Duplicate IDs/labels, changed labels, unknown visible IDs and limit violations return 400 atomically. Omitting a custom definition or removing its ID from visible lanes never deletes its definition or cards; restore its visibility to access the cards again. Lane move accepts only a non-negative integer `index` and moves the URL lane to that zero-based position among the currently visible lanes; larger indexes place it last. It applies to the latest saved order, so concurrent visibility changes are kept, and never touches definitions or cards. Unknown lanes, including another project's custom lanes, return 404; hidden lanes return 400. Add accepts nonempty unique decimal-string `issueIds`, all belonging to the URL project, and a visible destination lane. It validates the whole batch and inserts atomically; unknown/foreign IDs or hidden/invalid lanes return 400, any already-member ID returns 409 without moving it or adding any other IDs. Move accepts only a visible `lane`; missing membership returns 404. Remove deletes only membership/lane, leaving issue content, timestamps, comments and attachments untouched; missing membership returns 404. Missing projects return 404. All endpoints require authentication; writes require same-origin Origin. Full-access workspace members can collaborate; read-only access cannot write.

`PUT /api/projects/:slug/board/issues` accepts only `issueIds` (1–1000 unique decimal strings) and `lane` (a currently visible built-in or custom lane). It atomically adds missing memberships and moves existing memberships; placing an existing member in its current lane is a no-op. Unknown, foreign-project or unlinked issue IDs return 400, as do hidden/invalid destination lanes and invalid payloads. A missing project returns 404; an archived project returns 409, with active status rechecked inside the transaction. Closed issues already on the board may move, including from hidden lanes; closed off-board issues return 409 and must be reopened before adding. Any failure rolls back the entire batch. Only board membership/lane changes: issue content, timestamps, lifecycle, mentions, comments and board settings remain untouched. Issue counts remain unchanged; open counts reflect open memberships in non-Done lanes. Cookie authentication and same-origin protection apply, with full-access members allowed. Existing POST add-only, PATCH move-only and DELETE behavior is unchanged.

`POST /api/projects/:slug/board/issues/reorder` accepts exactly `issueIds` (1–1000 unique decimal strings), a visible destination `lane`, and required `beforeIssueId` (decimal string or null). It removes selected existing members from their old placements and inserts them as a block in supplied order before the anchor, or at the lane's end for null. The anchor must be an unselected current member in the destination lane. Unknown, foreign, unlinked or off-board targets and invalid anchors return 400; invalid/hidden destinations return 400; missing projects return 404 and archived projects 409. Closed existing cards can reorder. Authentication and same-origin protection apply. All validation and ordering use the latest complete board inside one immediate transaction: omitted/filtered-out cards retain relative order, and any failure rolls back the whole block. Repeating the same placement is a no-op. Reordering never changes issue data, timestamps, children, lifecycle or board definitions.

POST add, PUT placement and PATCH move append newly added/cross-lane cards to the destination in supplied order; same-lane placement retains its existing position. DELETE can leave internal gaps without affecting display order. Migration v10 adds an internal integer `board_issues.position`, initialized to each issue's number to preserve the old ascending-number order within every lane, including hidden/custom lanes. It is transactional/version-gated and preserves memberships, constraints, content, timestamps and children across restarts.

Issues expose no assignee, status, or priority. Creation accepts content (body plus optional backwards-compatible title), labels, optional `state:"open"|"draft"` (default open), and optional `lane`, plus optional `projectId` on the workspace-wide route only; `status`, `priority`, `assigneeId`, `addToBoard`, and other unknown fields are rejected with 400. Detail PATCH accepts only content, labels, `state`, and `projectId`; it rejects `assigneeId` (including null) and `lane`. Changing project removes old board membership but never assigns a destination lane. Issue responses select explicit public fields, excluding legacy assignee/status/priority. The old nullable SQLite `assigneeId` column and existing values are retained only as inactive historical data: no API reads or writes them, and they do not become tagged-user associations. `Project.issueCount` counts issues visible to the requesting user (other users' drafts are excluded); `Project.openCount` counts open issues on non-Done board cards, including hidden lanes, not unselected backlog.

`Issue.projectId` is `string | null`. Workspace creation with omitted/null `projectId` creates an unlinked issue; a string must identify an existing active project (404 unknown, 409 archived). Both creation routes accept optional `lane`: absent/null leaves the issue off-board; a non-null string (1–100 characters) must identify a currently visible built-in or custom lane in the selected active project. Invalid, hidden, foreign-project or unlinked lane placement returns 400. Validation, issue insertion, mention associations and appending the board card are one immediate transaction; failures leave no partial issue or placement. With a non-null lane the response includes the target project's `board`; otherwise it contains only `issue`. Issue numbers increment within each workspace across its projects and unlinked issues, starting at 1 for a new workspace.

Detail PATCH accepts optional `projectId:string|null` to move or unlink an existing issue. The source (if linked) and destination (if supplied and non-null) must be accessible and active: missing or inaccessible projects return 404 and archived projects return 409, including same-project requests on an archived project. Moves are limited to the same workspace and preserve the stable internal ID, workspace-local number, URL, content, comments, tags, tagged users and lifecycle unless other explicitly supplied fields change them. It removes the old board membership only when the project actually changes; a same-project request retains lane and position. Destination board placement is not automatic. Project, content and state edits share one transaction and all roll back on failure. The UI submits moves separately so unsaved body/comment drafts remain untouched. Unlinked issues support the same detail, content, lifecycle, comment and mention/label operations as linked issues, but cannot join any project board (400). Global bulk routes use the same payload limits, order, idempotence and atomicity as their project equivalents, accept mixed project/unlinked batches, and reject any archived-project target with 409 or missing issue with 404, rolling back all earlier targets. The existing project mention route is `/issues/tag`, whereas the global route is `/api/issues/tagged-users`.

Migration v9 transactionally rebuilds `issues` with nullable `projectId`, preserving legacy columns, data, constraints, explicit indexes/triggers and all child records/board memberships. Foreign-key actions are disabled outside the rebuild transaction, checked before commit, and re-enabled before returning the connection; failures roll back and close it. Existing `(projectId,number)` uniqueness remains, with a partial unique index enforcing `number` uniqueness for null project IDs. Migration is version-gated and safe across reopenings.

Migration v11 replaces UUID issue keys with `INTEGER PRIMARY KEY AUTOINCREMENT`, assigning existing issues sequential numbers in creation order (row insertion order breaks timestamp ties). `Issue.id`, `Comment.issueId`, and `BoardCard.issueId` are canonical positive decimal **strings**; At migration v11, `Issue.number` was the numeric alias of that ID; the workspace migration supersedes this with independent workspace-local numbers. IDs are globally unique and never reused. Bulk/board writes require canonical decimal strings, not UUIDs or JSON numbers. Other entities keep UUID IDs. The transactional migration updates live child relationships, preserves content/timestamps/lifecycle/board order and historical archives, and checks foreign keys. Its temporary UUID-to-number mapping is discarded after migration; old UUID URLs return 404. Back up before upgrade; rollback requires a pre-upgrade database.

References are plain `!12` in issue/comment prose, rendered as internal `/w/:workspaceSlug/issues/12` links in the containing issue's workspace. Code, HTML, images and existing links are excluded. `#12` remains a tag. Unknown reference numbers do not reject a body write; opening one returns the normal not-found response. Authenticated `GET /api/issues/references` searches accessible issues in the selected workspace by number (optional `!` prefix) or title and returns at most 20 `{id,number,title,state}` entries, without modifying issue associations.

`Issue.state` is `"open" | "closed" | "draft"`. Drafts derive from the internal `isDraft` flag; published issues derive their state from `Issue.closedAt`. PATCH `state:"closed"` sets `closedAt` (the update time) and `closedById` (the signed-in user); closing an already closed issue keeps both. `state:"open"` clears them. State may be combined with other fields and the whole PATCH is validated before any write. Closing or reopening alone never changes board membership or lanes; the UI omits closed issues from Add issues. List and board bulk close use individual state PATCH requests, not an atomic bulk endpoint: successful closes stay saved, failed issues remain available for retry, and already-closed issues are skipped.

`Issue.closeReason` is `"completed" | "not_planned" | "duplicate" | null`; `duplicateOfId` is a canonical decimal string or null. `POST /api/issues/:id/close` requires an open, accessible issue in an active project (or unlinked). It closes and optionally posts a comment in one transaction, including mention/attachment validation and history; any failure rolls everything back. Supplied comments must be nonblank after trimming and at most 100,000 characters; omit the field for closing without a comment. Duplicate closure requires a distinct accessible published target; drafts/inaccessible targets return 404, self/missing targets 400. Other reasons reject a supplied target. Archived targets may be referenced. Already-closed requests return 409 rather than posting duplicate comments on retry. Source drafts/archived projects also return 409. The target is filtered against current permissions on every issue read and becomes null if inaccessible; target identifiers/titles are never copied into history. History records `closeReason` as well as state and any comment. Existing PATCH and bulk close default to completed when closing an open issue, preserve reason/time/closer on redundant closes, and reopening clears all closure metadata. Neither action changes body or board placement. Migration 21 adds the nullable reason and target fields and backfills existing closures as completed without changing their timestamps or history. Back up before upgrade; rollback requires restoring the pre-upgrade backup.

The detail UI places a split close button beside Post comment. Choosing a reason (and a duplicate target, if applicable) does not close immediately. With a nonblank comment draft the action reads “Close with comment”; successful closure clears the posted comment but preserves unsaved issue-body edits. Reopening sits in the same location and preserves comment drafts. Publishing drafts remains a separate action.

Personal drafts are created with `state:"draft"` through either creation route. They require nonempty content like other issues and always start off-board (`lane` must be absent/null, otherwise 400). Only their creator can read or mutate them, including comments, history, search/reference results, and attachments, subject also to project access and archive restrictions. Mentions do not share drafts. Lists and project counts/recency exclude other users' drafts. Board add/place rejects the creator's draft with 409; other users receive the same 400 unknown-project-issue response as for nonexistent IDs to avoid existence probes. Boards never return draft cards.

PATCH `state:"open"` publishes the saved draft and its comments/history/attachments to its normal project/workspace audience, retaining ID, creator, content and creation time. Draft → closed and published → draft return 409 with no partial changes. Repeated draft → draft is allowed. Publishing records the draft → open history transition and does not place the issue on a board. The UI disables publication while body edits are unsaved and offers Draft in the State table filter; the default Open filter excludes it.

Migration v17 adds `isDraft` defaulting to 0, preserving existing open/closed issues and all other data. Earlier application versions do not enforce draft privacy and must not run against this database; restore a pre-upgrade backup for rollback.

`Project.archivedAt` and `Project.archivedById` are null for active projects. `Issue.taggedUserIds` is a sorted, deduplicated array of user UUIDs derived from actual Markdown mention links (`[@Display Name](mention:UUID)`) across the saved issue and its comments. `POST /api/projects/:slug/issues/tag` accepts only `issueIds` and `userIds`, each a nonempty array of at most 1000 unique IDs: canonical decimal strings for issues, UUIDs for users. All issues must belong to the URL project and all users must exist. `Issue.labels` is derived from hashtags in saved issue-body prose, deduplicated in encounter order. Bare labels must match `/^[a-z0-9]+(?:-[a-z0-9]+)*$/`: lowercase ASCII letters/digits with single separating hyphens; body hashtags prefix these with `#` (for example `#needs-review` or `#release-2`). Uppercase, Unicode, underscores, spaces, leading/trailing or repeated hyphens, and bracket/percent-encoded extended syntax are unsupported. Invalid full tokens such as `#bugFix`, `#bug_bad`, `#bug--fix`, `#-bug`, `#bug-`, and `#[needs%20review]` remain plain prose, never truncated into valid tags. Code, HTML, links, URLs, images and definitions are excluded; comment hashtags do not contribute. Markdown escapes are interpreted semantically, so `\\#bug` counts as `bug`. Writes validate at most 30 labels of up to 50 characters. Legacy POST/PATCH `labels` arrays are additive compatibility input converted into missing body hashtags, not a replacement label list; `labels:[]` does not clear hashtags. These arrays accept only valid bare labels, without `#` and without trimming, case folding or decoding; any invalid entry returns 400 atomically. Remove hashtags from `body` to remove labels. Final body and label limits are validated atomically.

`POST /api/projects/:slug/issues/labels` accepts only `issueIds` (1–1000 unique decimal strings) and `labels` (1–30 bare labels matching `/^[a-z0-9]+(?:-[a-z0-9]+)*$/`, each at most 50 characters, without the hashtag prefix). Labels are validated as supplied: surrounding whitespace and any invalid entry return 400, rather than being trimmed or silently dropped. It atomically appends missing hashtags to the latest saved bodies; duplicate requested/existing labels are skipped. Unclosed Markdown blocks may require insertion near the top instead. Stored titles, comments, mentions, lifecycle and board placement are preserved; timestamps change only when content changes. All issues must belong to the URL project: missing projects/issues return 404, foreign issues or invalid input return 400, and archived projects return 409. Any resulting body over 101000 characters or combined label set over 30 labels rejects the entire batch. Responses follow submitted issue order; retries are idempotent. The usual cookie authentication and same-origin write protection apply.
