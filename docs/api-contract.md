# Internal API contract

All API responses are JSON; errors `{ error: string }`. Objects use `shared/types.ts` exactly. All `/api` routes except auth status/setup/login/OIDC require cookie authentication. Unsafe methods require a same-origin `Origin` header. Auth cookies are HttpOnly, SameSite=Lax, and Secure in HTTPS. Runtime OIDC configuration requires admin. Body content is canonical Markdown, not HTML.

Favorites are stored per authenticated user, never on the shared `Project` object. PUT/DELETE require same-origin protection and use the session user only; a body cannot select another user. Both return the complete saved project-ID list sorted by ID. Unknown projects return 404 on either write. Archived projects can be favorited/unfavorited, and archiving never deletes favorites; clients hide archived favorites until restoration.

Issue history is authenticated and readable for archived projects. `IssueHistoryEntry` contains `id:number`, `issueId:string`, `actorId:string`, `createdAt:string` (ISO timestamp), `action` (`created`, `updated`, `commented`, `comment_edited`, `comment_deleted`), and `changes` (`{field,before,after}[]`). Fields are `body`, `state`, `project`, `boardLane`, or `comment`; values are string or null. Bodies/comments retain complete Markdown snapshots, state is open/closed, and project/lane values snapshot readable names (null means no project/not on board). Creation records initial non-null values with null before; subsequent combined edits are one event per changed issue. Identity changes between equally named projects still record an event. All board membership routes record additions/removals/lane changes; ordering alone, lane visibility/order, project renaming, and no-op writes do not. Bulk body labels/mentions record body changes. Comments record their create/edit/delete snapshots. Events commit in the same transaction as mutations; failed writes cannot leave events. Pagination orders by history ID descending, not timestamp; `before` is an exclusive positive safe-integer decimal cursor. `limit` defaults to 50 and accepts 1–100; invalid cursors/limits return 400. Missing/malformed issue IDs return 404. Fetch the next page using the last returned event ID; `hasMore` is computed using one extra row.

Migration v12 additively creates history and user/project favorite tables and a history pagination index. It never backfills fictional pre-upgrade events, truncates saved history, or resets favorites. Historical migration fixtures may still request targetVersion 10 or 11; normal startup upgrades to 12.

Project metadata PATCH requires at least one of `name` (trimmed, 1–100 characters) or `description` (0–10,000 characters, empty clears it). Omitted fields are preserved. Unknown keys, empty payloads and combining metadata with `archived` return 400. Any authenticated member may edit an active project, with same-origin CSRF protection; archived metadata edits return 409 until restored separately. Updates are transactional and preserve `id`, `slug`, `createdAt`, lifecycle fields, counts, issues, comments and board configuration/membership. Renaming never changes existing URLs.

Issue content is a single Markdown `body` (maximum `ISSUE_BODY_MAX_LENGTH = 101000` characters). Body-only POST/PATCH requires non-whitespace content. `Issue.title` remains a derived display cache: first ATX/setext heading outside fenced/indented code, otherwise the first meaningful text line, with common inline markup/links removed and a 300-character maximum; image/code-only content displays `Untitled issue`. `deriveIssueTitle` is exported by `shared/issue-content.ts`. State-only and project-only PATCH preserve content and cache. For legacy clients, optional nonempty `title` (max 300) is merged into the body as an escaped leading heading on POST or PATCH with body; an equivalent existing leading heading is not duplicated. Title-only PATCH replaces/adds the leading heading and preserves the remainder. The final merged body must fit the body limit. SQLite migration v3 transactionally prepends each old title as an escaped heading (unless an equivalent heading already leads the body), preserving original body bytes and all timestamps/metadata, and recomputes the title cache. Migration runs once, safely across reopenings.

`Lane` is a string ID. Built-in `LANES` are `todo`, `in_progress`, and `done`, labelled Todo, In progress, Done in that default order. `BoardLane` is `{value:Lane,label:string}`, `BoardCard` is `{issueId:string,lane:Lane}`, and `BoardSettings` is `{lanes:Lane[],customLanes:BoardLane[],cards:BoardCard[]}`. Cards include all explicitly selected work, even in hidden lanes. Each lane's subsequence in the cards array defines its persisted display order; clients must not re-sort by issue number. Cards expose no position field. New boards default to all three visible lanes, no custom definitions and no cards. PATCH board accepts nonempty unique known `lanes` and optional `customLanes`, stores `lanes` in the submitted order (the board's left-to-right display order), and never touches cards. Custom definitions are project-specific, merged additively and immutable: IDs must be lowercase `custom_<UUID v4>`, labels are trimmed to 1–60 characters and unique case-insensitively including default names, and there may be at most 30 custom definitions. Duplicate IDs/labels, changed labels, unknown visible IDs and limit violations return 400 atomically. Omitting a custom definition or removing its ID from visible lanes never deletes its definition or cards; restore its visibility to access the cards again. Lane move accepts only a non-negative integer `index` and moves the URL lane to that zero-based position among the currently visible lanes; larger indexes place it last. It applies to the latest saved order, so concurrent visibility changes are kept, and never touches definitions or cards. Unknown lanes, including another project's custom lanes, return 404; hidden lanes return 400. Add accepts nonempty unique decimal-string `issueIds`, all belonging to the URL project, and a visible destination lane. It validates the whole batch and inserts atomically; unknown/foreign IDs or hidden/invalid lanes return 400, any already-member ID returns 409 without moving it or adding any other IDs. Move accepts only a visible `lane`; missing membership returns 404. Remove deletes only membership/lane, leaving issue content, timestamps, comments and attachments untouched; missing membership returns 404. Missing projects return 404. All endpoints require authentication; writes require same-origin Origin. Every signed-in workspace member can collaborate.

`PUT /api/projects/:slug/board/issues` accepts only `issueIds` (1–1000 unique decimal strings) and `lane` (a currently visible built-in or custom lane). It atomically adds missing memberships and moves existing memberships; placing an existing member in its current lane is a no-op. Unknown, foreign-project or unlinked issue IDs return 400, as do hidden/invalid destination lanes and invalid payloads. A missing project returns 404; an archived project returns 409, with active status rechecked inside the transaction. Closed issues already on the board may move, including from hidden lanes; closed off-board issues return 409 and must be reopened before adding. Any failure rolls back the entire batch. Only board membership/lane changes: issue content, timestamps, lifecycle, mentions, comments and board settings remain untouched. Issue counts remain unchanged; open counts reflect open memberships in non-Done lanes. Cookie authentication and same-origin protection apply, with signed-in members allowed. Existing POST add-only, PATCH move-only and DELETE behavior is unchanged.

`POST /api/projects/:slug/board/issues/reorder` accepts exactly `issueIds` (1–1000 unique decimal strings), a visible destination `lane`, and required `beforeIssueId` (decimal string or null). It removes selected existing members from their old placements and inserts them as a block in supplied order before the anchor, or at the lane's end for null. The anchor must be an unselected current member in the destination lane. Unknown, foreign, unlinked or off-board targets and invalid anchors return 400; invalid/hidden destinations return 400; missing projects return 404 and archived projects 409. Closed existing cards can reorder. Authentication and same-origin protection apply. All validation and ordering use the latest complete board inside one immediate transaction: omitted/filtered-out cards retain relative order, and any failure rolls back the whole block. Repeating the same placement is a no-op. Reordering never changes issue data, timestamps, children, lifecycle or board definitions.

POST add, PUT placement and PATCH move append newly added/cross-lane cards to the destination in supplied order; same-lane placement retains its existing position. DELETE can leave internal gaps without affecting display order. Migration v10 adds an internal integer `board_issues.position`, initialized to each issue's number to preserve the old ascending-number order within every lane, including hidden/custom lanes. It is transactional/version-gated and preserves memberships, constraints, content, timestamps and children across restarts.

Issues expose no assignee, status, or priority. Creation accepts content (body plus optional backwards-compatible title), labels, and optional `lane`, plus optional `projectId` on the workspace-wide route only; `status`, `priority`, `assigneeId`, `addToBoard`, `state`, and other unknown fields are rejected with 400. Detail PATCH accepts only content, labels, `state`, and `projectId`; it rejects `assigneeId` (including null) and `lane`. Changing project removes old board membership but never assigns a destination lane. Issue responses select explicit public fields, excluding legacy assignee/status/priority. The old nullable SQLite `assigneeId` column and existing values are retained only as inactive historical data: no API reads or writes them, and they do not become tagged-user associations. `Project.issueCount` counts all issues; `Project.openCount` counts open issues on non-Done board cards, including hidden lanes, not unselected backlog.

`Issue.projectId` is `string | null`. Workspace creation with omitted/null `projectId` creates an unlinked issue; a string must identify an existing active project (404 unknown, 409 archived). Both creation routes accept optional `lane`: absent/null leaves the issue off-board; a non-null string (1–100 characters) must identify a currently visible built-in or custom lane in the selected active project. Invalid, hidden, foreign-project or unlinked lane placement returns 400. Validation, issue insertion, mention associations and appending the board card are one immediate transaction; failures leave no partial issue or placement. With a non-null lane the response includes the target project's `board`; otherwise it contains only `issue`. Issue numbers increment globally across all projects and unlinked issues, starting at 1.

Detail PATCH accepts optional `projectId:string|null` to move or unlink an existing issue. The source (if linked) and destination (if supplied and non-null) must exist and be active: missing projects return 404 and archived projects return 409, including same-project requests on an archived project. The move preserves the global ID/number, URL, content, comments, tags, tagged users and lifecycle unless other explicitly supplied fields change them. It removes the old board membership only when the project actually changes; a same-project request retains lane and position. Destination board placement is not automatic. Project, content and state edits share one transaction and all roll back on failure. The UI submits moves separately so unsaved body/comment drafts remain untouched. Unlinked issues support the same detail, content, lifecycle, comment and mention/label operations as linked issues, but cannot join any project board (400). Global bulk routes use the same payload limits, order, idempotence and atomicity as their project equivalents, accept mixed project/unlinked batches, and reject any archived-project target with 409 or missing issue with 404, rolling back all earlier targets. The existing project mention route is `/issues/tag`, whereas the global route is `/api/issues/tagged-users`.

Migration v9 transactionally rebuilds `issues` with nullable `projectId`, preserving legacy columns, data, constraints, explicit indexes/triggers and all child records/board memberships. Foreign-key actions are disabled outside the rebuild transaction, checked before commit, and re-enabled before returning the connection; failures roll back and close it. Existing `(projectId,number)` uniqueness remains, with a partial unique index enforcing `number` uniqueness for null project IDs. Migration is version-gated and safe across reopenings.

Migration v11 replaces UUID issue keys with `INTEGER PRIMARY KEY AUTOINCREMENT`, assigning existing issues sequential numbers in creation order (row insertion order breaks timestamp ties). `Issue.id`, `Comment.issueId`, and `BoardCard.issueId` are canonical positive decimal **strings**; `Issue.number` is the numeric alias of that ID. IDs are globally unique and never reused. Bulk/board writes require canonical decimal strings, not UUIDs or JSON numbers. Other entities keep UUID IDs. The transactional migration updates live child relationships, preserves content/timestamps/lifecycle/board order and historical archives, and checks foreign keys. Its temporary UUID-to-number mapping is discarded after migration; old UUID URLs return 404. Back up before upgrade; rollback requires a pre-upgrade database.

References are plain `!12` in issue/comment prose, rendered as internal `/issues/12` links. Code, HTML, images and existing links are excluded. `#12` remains a tag. Unknown reference numbers do not reject a body write; opening one returns the normal not-found response. Authenticated `GET /api/issues/references` searches globally by number (optional `!` prefix) or title and returns at most 20 `{id,number,title,state}` entries, without modifying issue associations.

`Issue.state` is `"open" | "closed"`, derived from `Issue.closedAt`. PATCH `state:"closed"` sets `closedAt` (the update time) and `closedById` (the signed-in user); closing an already closed issue keeps both. `state:"open"` clears them. State may be combined with other fields and the whole PATCH is validated before any write. Closing or reopening alone never changes board membership or lanes; the UI omits closed issues from Add issues. List and board bulk close use individual state PATCH requests, not an atomic bulk endpoint: successful closes stay saved, failed issues remain available for retry, and already-closed issues are skipped.

`Project.archivedAt` and `Project.archivedById` are null for active projects. PATCH `{archived:true}` records the time and signed-in user; repeating it keeps the original values. `{archived:false}` restores the project. Any signed-in member may archive or restore. `GET /api/projects` returns active and archived projects; the UI hides archived ones from navigation. Archived projects remain readable, but issue creation and updates (including state), comment creation/edit/delete, and every board write (settings, lane moves, add/move/remove cards) return 409 `Project is archived` without changes. Authorization (404, 403) is checked first. Uploads are workspace-wide and unaffected.

SQLite migration v4 stores cards separately in `board_issues`, with unique project/issue membership, lane checks and a composite project/issue foreign key. It archives old settings as `legacy_project_boards` and retains original issue status/priority columns internally. Explicit legacy issueIds selections are preserved, mapping Backlog placement to Todo. Legacy automatic null selection or no board settings imports only Todo/In progress/Done issues, never Backlog. Visible Backlog maps to Todo and lanes are deduplicated/canonicalized; empty results default to all three. Other records and timestamps remain untouched. The forward migration is transactional and version-gated across reopenings; later issues remain off-board unless creation explicitly supplies a visible `lane` or a board placement operation adds them.

SQLite migration v5 adds `project_boards.customLanes` (default `[]`) and transactionally rebuilds `board_issues` without its default-only lane check, retaining the membership primary key, composite foreign key and all existing placements. Lane validity and visibility are enforced by the board API. The migration is version-gated and preserves existing lane visibility.

SQLite migration v6 adds nullable `issues.closedAt`, `issues.closedById`, `projects.archivedAt` and `projects.archivedById` (user references), so existing issues stay open and projects stay active. It is transactional and version-gated, adds only missing columns, and never resets existing values. Inserts name their columns because the tables grew.

`Issue.taggedUserIds` is a sorted, deduplicated array of user UUIDs derived from actual Markdown mention links (`[@Display Name](mention:UUID)`) across the saved issue and its comments. No role/source metadata or notifications are attached. Plain text, code examples, and images are not mentions; real reference links are supported. New content referring to an unknown valid user UUID returns 400 atomically. Mention edits/deletes recalculate the union in the content-write transaction; removing the last reference removes the association. Comment mutation responses include the updated issue so clients can refresh associations without replacing unsaved issue drafts. Migration v7 creates `issue_tagged_users(issueId,userId)` with a composite primary key and foreign keys, backfilling known IDs only while preserving content and timestamps.

`POST /api/projects/:slug/issues/tag` accepts only `issueIds` and `userIds`, each a nonempty array of at most 1000 unique IDs: canonical decimal strings for issues, UUIDs for users. All issues must belong to the URL project and all users must exist. Missing projects/issues return 404; foreign issues, unknown users, invalid input, or a resulting body over 101000 characters return 400; archived projects return 409. The entire batch rolls back on failure. It adds missing body mention links without rewriting original Markdown or comments, preserves stored titles and lifecycle/board data, updates `updatedAt` only when content changes, and recalculates labels and tagged-user associations. Repeating the same request is idempotent, including timestamps; comment-only mentions do not suppress new body mentions. Responses follow the submitted issue order.

`Issue.labels` is derived from hashtags in saved issue-body prose, deduplicated in encounter order. Bare labels must match `/^[a-z0-9]+(?:-[a-z0-9]+)*$/`: lowercase ASCII letters/digits with single separating hyphens; body hashtags prefix these with `#` (for example `#needs-review` or `#release-2`). Uppercase, Unicode, underscores, spaces, leading/trailing or repeated hyphens, and bracket/percent-encoded extended syntax are unsupported. Invalid full tokens such as `#bugFix`, `#bug_bad`, `#bug--fix`, `#-bug`, `#bug-`, and `#[needs%20review]` remain plain prose, never truncated into valid tags. Code, HTML, links, URLs, images and definitions are excluded; comment hashtags do not contribute. Markdown escapes are interpreted semantically, so `\\#bug` counts as `bug`. Writes validate at most 30 labels of up to 50 characters. Legacy POST/PATCH `labels` arrays are additive compatibility input converted into missing body hashtags, not a replacement label list; `labels:[]` does not clear hashtags. These arrays accept only valid bare labels, without `#` and without trimming, case folding or decoding; any invalid entry returns 400 atomically. Remove hashtags from `body` to remove labels. Final body and label limits are validated atomically.

`POST /api/projects/:slug/issues/labels` accepts only `issueIds` (1–1000 unique decimal strings) and `labels` (1–30 bare labels matching `/^[a-z0-9]+(?:-[a-z0-9]+)*$/`, each at most 50 characters, without the hashtag prefix). Labels are validated as supplied: surrounding whitespace and any invalid entry return 400, rather than being trimmed or silently dropped. It atomically appends missing hashtags to the latest saved bodies; duplicate requested/existing labels are skipped. Unclosed Markdown blocks may require insertion near the top instead. Stored titles, comments, mentions, lifecycle and board placement are preserved; timestamps change only when content changes. All issues must belong to the URL project: missing projects/issues return 404, foreign issues or invalid input return 400, and archived projects return 409. Any resulting body over 101000 characters or combined label set over 30 labels rejects the entire batch. Responses follow submitted issue order; retries are idempotent. The usual cookie authentication and same-origin write protection apply.

Migration v8 transactionally adds missing valid legacy-label hashtags and rebuilds the label cache once; invalid legacy names are skipped. It preserves original body content, stored titles, timestamps, lifecycle history, comments and board placements. Earlier releases used extended tags for legacy punctuation/whitespace; that syntax is no longer recognized as labels. Insertion may be before an unclosed code/HTML block so new valid hashtags are real prose.

Migration v13 rebuilds the stored label index from existing bodies using the kebab-tag grammar, removing unsupported labels from filters and suggestions. Bodies, titles, timestamps, lifecycle and history are unchanged; existing text is not converted to lowercase kebab tags.

Comment bodies require non-whitespace content and remain limited to 100000 characters. Issue creation uses one autofocus Markdown editor, with no separate title field.

UI uses URL routes `/projects` (`?view=archived` lists archived projects), `/projects/:slug` (`?state=closed` lists closed issues), `/projects/:slug/board`, `/issues/:id`, `/admin`. Auth status gates all application screens. Login/setup rendered when status says unauthenticated.

Editor component contract: `RichEditor({value:string,onChange:(markdown:string)=>void,placeholder?:string,minimal?:boolean,ariaLabel?:string,autoFocus?:boolean,mentionUsers?:User[]})`, exported from `src/components/rich-editor.tsx`. Markdown renderer `Markdown({children:string,mentionUsers?:User[]})` from `src/components/markdown.tsx`. Editors own uploads via `/api/uploads`. UI shared API helper `api<T>(path, RequestInit?)` in `src/lib/api.ts`; credentials same-origin; throws Error with API message. Editor may use api or fetch independently.
